# v1.1: Find Your Hill + HitWhereItHurts. Scope challenge and implementation plan

Status: plan agreed before coding. Both modules are additive, behind separate feature flags (default **off**), and do not touch the Delhi compliance engine, the public-launch verification gates, or `rc:check`.

## 1. The human experience, as a bounded specification
- **Find Your Hill (FYH):** a visitor with no account searches issues by keyword, place and topic, reads a neutral issue page (what it is, why it is discussed, sourced evidence, different perspectives, disputed claims, what is unknown, when it was last checked) and sees related protests and digital actions. Following an issue needs a confirmed-email account; reading never does.
- **Digital Actions (working name HitWhereItHurts, HWIH):** an organizer attaches a campaign to a published issue, states one specific requested change, cites evidence, offers only lawful, nonviolent action choices from a fixed list, and sets a start date, review date and closure criteria. Participants follow, mark interest, say which action they intend to take and may self-report completing it. Everything is aggregate-only and withdrawable. Outcomes are recorded in three separate lanes.
- **Physical protests:** unchanged. A protest page may point at an issue; an issue page lists linked public protests. Neither requires the other.

## 2. What is reused, what is new
| Need | Reused | New (additive migration `012`) |
|---|---|---|
| Accounts, verified email, rate limits | `users.email_verified_at`, `requireVerified`, `allow()` | none |
| Aggregate-only participation | pattern of `protest_supports` (join on confirmed, non-suspended users) | `issue_followers`, `digital_campaign_participation`, `digital_campaign_action_intents` (the protest tables are keyed to protests) |
| Provenance labels | `Provenance` component | one class `EXTERNAL_SOURCE_LINK` ("Link to independent source") |
| Reports and moderation | reasons list, `moderation_actions`, `audit_log`, admin patterns | `content_reports`, `content_corrections`; `moderation_actions.issue_id/campaign_id`; reason `FACTUAL_ERROR` (reports only) |
| Name/identity signals | `identity.ts` | none |
| Source registry | **not reused**: it holds legal-rule evidence for the Delhi engine | `issue_sources` (issue evidence is deliberately separate from legal compliance rules) |
| Analytics | `track()` + prop whitelist | 9 event names, same dimensions |

## 3. Ambiguities and risks challenged
1. **Can a boycott module be politically neutral?** Neutrality can only be a property of the *rules*, not of the topics: the same evidence, correction, no-individuals and no-harassment rules apply to every campaign; no ranking by desired harm; no targeting by belief; no featured campaigns. The platform cannot make a campaign about a named company "neutral"; it can make it accountable (citations, dispute route, correction notices, moderation by conduct).
2. **Defamation/intermediary exposure is real and not solved by code.** A campaign naming an institution makes factual claims about it. Mitigations built: citations required to publish, a correction route open to anyone (including the institution), published corrections shown on the page, state `DISPUTED`, hide only for conduct reasons. Legal review of this module (naming, notice-and-action duties, liability) is a **precondition for enabling it publicly** and is not claimed done.
3. **"HitWhereItHurts" names an intent to cause harm.** The UI uses "Digital Actions" and shows the working name only as a kicker. Recommendation: rename before launch.
4. **Catalogue integrity.** This environment cannot reach most official sites and I will not invent sources. The product ships with an **empty catalogue**; issues are authored and published only by a human admin and need an https source, a "what remains unknown" statement, a check date and a neutral description. Test fixtures are labelled as fixtures. Whether any real issue's sources are accurate is a human editorial task this build cannot verify.
5. **AI.** No AI service is added. Suggestions from users go to a human review queue; nothing is auto-published.
6. **Counts can mislead.** Totals count confirmed-email accounts only, "completed" is always "self-reported, not verified", and nothing converts participation into revenue/impact. There is no field for financial impact at all in v1 (deferred).
7. **Success claims.** No independent verification method exists, so the product never shows "verified success". `RESOLVED_REPORTED` always reads "reported by organizer", with "no independent evidence recorded" or "source linked" beneath.
8. **Brigading via reports.** Reports queue for a human and never hide anything. A `FACTUAL_ERROR` report can only be dismissed or answered with a correction; it cannot remove a page (removal needs a conduct reason), so unpopular-but-sourced views are not deleted for being disputed.

## 4. Frozen out of scope (v1.1)
Payments, fundraising, donations, political ads, targeting by profile or belief, AI summarisation or crawling, supporter exports, receipt/purchase upload, financial-impact estimates, harassment/spam tooling, messaging, auto-selection of targets (companies, donors, people), native app, new jurisdictions, any change to the Delhi rules engine or to launch gates, deployment, enabling either flag.

## 5. Implementation plan (smallest coherent vertical slice)
1. Flags: `FEATURE_FIND_YOUR_HILL`, `FEATURE_HIT_WHERE_IT_HURTS` (off = routes 404, no navigation, no analytics).
2. Migration `012_issues_and_digital_actions.sql`.
3. Pure engines (`issues.ts`, `digital-action.ts`) with publish gates, text screening, outcome labelling.
4. Services (`issues`, `digital-actions`, `content-moderation`).
5. UI: `/issues`, `/issues/[slug]`, `/issues/suggest`, `/actions`, `/actions/new`, `/actions/[slug]`, `/actions/[slug]/manage`, `/activity`, `/admin/issues`, `/admin/content`; nav entries only when flagged on.
6. Tests: pure, DB, code-scan (participation tables only in their service), browser scenarios A–F, regression G, accessibility.
7. Docs: the two acceptance notes, learning capture. Commit to the same branch; no deploy.
